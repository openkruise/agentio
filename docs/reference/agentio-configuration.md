# Agentio configuration

Agentio extends the [Istio configuration model](https://istio.io/latest/docs/reference/config/) with controller configuration for egress routing, external policy processing, egress gateways, TLS termination, and connection controls. This page describes the Agentio-specific configuration stored in Kubernetes ConfigMaps.

A **Sandbox** is an OpenKruise Sandbox workload, the unit of identity and policy subject in Agentio.

## Configuration sources and precedence

Agentio builds the effective configuration in the mesh root namespace, which is `agentio-system` in the standard chart installation. Each ConfigMap stores YAML in `data.config`.

The sources are applied in this order:

| Priority | Source | Purpose |
| --- | --- | --- |
| 1 | `agentio-config` | Contains chart-generated defaults plus the raw configuration under `agentiod.config.values`. |
| 2 | `agentio-config-primary` | Optionally overrides the base configuration. |

Both ConfigMaps are watched. A valid update is applied and distributed without restarting `agentiod`. If a layer cannot be parsed or validated, Agentio logs a warning and retains the last successfully applied effective configuration.

Unknown fields are ignored with a warning listing their full paths, so an older controller can read configuration that contains fields from a newer version. Known fields still undergo type and semantic validation; invalid enum names, duplicate YAML keys, and conflicting oneof members reject the update. Before any valid configuration has been loaded, rejection uses the startup defaults; retained configuration does not survive a process restart.

## Merge behavior

Configuration is merged by protobuf field semantics:

- A top-level field omitted by a higher-priority layer preserves the lower-priority value.
- A message field present in a higher-priority layer replaces that entire message. Include every nested field that must remain set.
- A repeated field present in a higher-priority layer replaces the entire lower-priority list; list entries are not appended.
- An empty document or `{}` preserves the lower-priority configuration.

For example, this primary layer replaces the complete `sandboxExtProc` message. It changes `service` and resets the lower layer's `port` and processing options:

```yaml
sandboxExtProc:
  service: primary-extension.agentio-system.svc.cluster.local
```

To preserve the port, repeat it explicitly:

```yaml
sandboxExtProc:
  service: primary-extension.agentio-system.svc.cluster.local
  port: 9002
```

The Helm-only merge happens earlier: `.Values.agentiod.config.values` is merged over the chart-generated base document, with maps deep-merged and lists replaced. The resulting YAML becomes `agentio-config`; runtime precedence between the base and primary ConfigMaps then follows the rules above.

## Configure the Helm-managed base

Use the chart's task-oriented values for common settings and `agentiod.config.values` for the raw configuration API:

```yaml
agentiod:
  config:
    values:
      egressPolicies:
        - namespaces:
            - agent-demo
          matchHosts:
            - api.example.com
          policy: GATEWAY
          gateway:
            service: agentio-egress.agentio-system.svc.cluster.local
        - namespaces:
            - agent-demo
          policy: PASSTHROUGH
      egressGateways:
        - name: agentio-egress
          namespace: agentio-system
          tcp:
            idleTimeout: 30m
```

Render the generated base before applying it:

```console
$ helm template agentio ./manifests/charts/agentio \
    --namespace agentio-system \
    --values values.yaml \
  | sed -n '/name: agentio-config$/,/^---$/p'
```

## Configure the primary override

Create `agentio-config-primary` only when another deployment or operations layer must override the Helm-managed base. Keep the complete value of every message or repeated field that the primary layer owns:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: agentio-config-primary
  namespace: agentio-system
data:
  config: |
    egressPolicies:
    - namespaces:
      - agent-demo
      matchHosts:
      - api.example.com
      policy: GATEWAY
      gateway:
        service: primary-egress.agentio-system.svc.cluster.local
    - namespaces:
      - agent-demo
      policy: PASSTHROUGH
```

In this example the primary `egressPolicies` list replaces the complete list generated by Helm. Editing only `agentio-config` will not change the effective route while this primary list exists.

## Top-level fields

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `sandboxExtProc` | `ExtProcProvider` | Unset | Global external-processing provider used by egress gateways unless a gateway supplies an override. |
| `additionalExtProcs` | `ExtProcProvider[]` | Empty | Ordered processors appended after the effective sandbox provider. Disabled when that provider is absent or explicitly disabled. |
| `egressPolicies` | `EgressPolicy[]` | Empty | Ordered egress routing rules. The first matching policy is applied. |
| `egressAuthorization` | `EgressAuthorization` | Built-in destination restrictions | Additional denied destination CIDRs for all native Envoy egress gateways, independently of EPE. |
| `sandboxIgnoredLabels` | `string[]` | Built-in list | Label names or path-style patterns removed from Sandbox workload metadata to reduce configuration size. |
| `egressGateways` | `EgressGateway[]` | Empty | Per-gateway HTTP, TCP, TLS, external processing, and CONNECT limit settings. |
| `trustedEPEIdentities` | `string[]` | Empty; Helm adds the managed EPE identity | Exact SPIFFE identities authorized for EPE Workload and TrafficPolicy discovery. Empty disables EPE access. |

## Egress authorization

Use `egressAuthorization.deniedCIDRs` to prevent native gateways from connecting to selected destination networks. Put this fragment in ConfigMap `data.config`, or under `agentiod.config.values` when using Helm:

```yaml
egressAuthorization:
  deniedCIDRs:
    - 100.100.100.200/32
    - 192.0.2.0/24
```

This applies to all native gateways, including gateways with EPE disabled. TCP and HTTP forwarding check the destination selected for the actual upstream connection, including ServiceEntry and EPE-selected targets. The outer TCP CONNECT tunnel does not reject its original destination before target selection; an allowed final target can differ from the original address. A matching `tcpPassthrough` entry or an EPE allow decision cannot override a denial of the final target. Plaintext application-level CONNECT uses `ORIGINAL_DST` with an HTTP RBAC check of the actual proxy IP before forwarding; HTTPS proxy connections use DFP with outer-SNI target selection. Destinations reached by the external proxy are outside this check. Internal connections to Porter, EPE, and the control plane are excluded.

Loopback (`127.0.0.0/8`, `::1/128`), unspecified (`0.0.0.0/32`, `::/128`), and link-local (`169.254.0.0/16`, `fe80::/10`) destinations are always denied, including equivalent IPv4-mapped IPv6 addresses. This also applies to original TCP traffic that does not use DNS. Private service networks remain allowed unless listed. The Alibaba Cloud metadata address `100.100.100.200` requires an explicit entry, as shown above.

Entries must be IPv4 or IPv6 CIDRs; use `/32` or `/128` for one address. Hostnames, bare IPs, scoped IPv6 addresses, and IPv4-mapped IPv6 CIDRs are invalid. An omitted or null block inherits the lower layer; a supplied block replaces inherited user entries. `egressAuthorization: {deniedCIDRs: []}` clears user entries while retaining built-ins. Invalid updates retain the last valid AgentioConfig.

Custom EnvoyFilter patches must preserve the destination checks, including the HTTP RBAC filter for plaintext application-level CONNECT.

Updates are distributed through xDS without restarting the gateway and take effect after it accepts the new resources. Existing connections are not forcibly closed. A changed effective list uses a separate DNS cache so previously cached targets cannot bypass the new list. Superseded caches remain allocated until Envoy restarts; restart gateways periodically if this list changes frequently.

`EPEConfig.egressAuthorization` remains an independent setting. The gateway rejects a denied address even when EPE explicitly selected it, without trying a different address. Configure the same custom CIDRs in EPE when EPE should exclude them while choosing among DNS candidates, or when EPE is deployed independently. AgentioConfig does not distribute this list to EPE.

Legacy proxyv2 gateways do not support this setting. A nonempty custom list suppresses the legacy gateway resource variant; upgrade gateways to the native image before configuring it. Native gateways always enforce the built-ins. See [destination restrictions](../design/egress-gateway-protocol-and-dfp.md#destination-restrictions) for DNS behavior.

## Trusted EPE identities

Register every EPE discovery client in the effective configuration. EPE always requires workload discovery access to resolve Workload SecurityProfile references, including when TrafficPolicy authorization is disabled:

```yaml
trustedEPEIdentities:
  - spiffe://cluster.local/ns/agentio-system/sa/agentio-epe
  - spiffe://cluster.local/ns/custom-system/sa/custom-ext-proc
```

The trust domain must match the client's verified workload principal. `agentiod` validates a Pod-bound ServiceAccount token using the configured Kubernetes workload authenticator (`local` by default) and checks its active Pod binding before matching the workload principal exactly against this list. The client must also present the EPE node type. Node metadata cannot declare a trusted identity, and wildcards are not supported. Authorized EPE clients can discover Workloads and TrafficPolicies, not gateway configuration or secrets.

Helm adds the managed EPE's identity using `global.trustDomain`, the release namespace, and `epe.serviceAccount.name`. For external EPE deployments, configure `agentiod.config.values.trustedEPEIdentities` explicitly. A supplied list replaces the generated list, so include every EPE identity that should retain access. Set `trustedEPEIdentities: []` to disable access.

Updates apply to newly established discovery streams without restarting `agentiod`. Removing an identity does not immediately terminate an existing stream; it is checked again when the client reconnects.

## Egress policies

Agentio evaluates `egressPolicies` in document order. Put specific rules first and a broad `PASSTHROUGH` or `GATEWAY` fallback last. Use TrafficPolicy for access control.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `namespaces` | `string[]` | Empty | Source workload namespaces. Empty matches every namespace. |
| `matchHosts` | `string[]` | Empty | Destination hostnames. The control plane resolves them, refreshes results according to DNS TTL, and adds the addresses to the CIDR match. |
| `matchCidrs` | `string[]` | Empty | Destination CIDRs. Empty matches every destination address. |
| `matchPorts` | `string[]` | Empty | Decimal destination ports such as `"443"`. Empty matches every port. CIDR/host and port conditions must both match when both are set. |
| `policy` | Enum | `PASSTHROUGH` | `PASSTHROUGH` connects directly and `GATEWAY` forwards to `gateway`. Legacy `DENY` is not supported by native Sandbox routing; migrate rejection rules to TrafficPolicy. |
| `gateway.service` | String | Empty | Fully qualified or resolvable Service name of the egress gateway used by a `GATEWAY` action. |
| `gateway.port` | Integer | `0` | Gateway target port. Set it explicitly when the target does not use the data plane's standard gateway port. |

Example with a gateway route and passthrough fallback:

```yaml
egressPolicies:
  - namespaces: [agent-demo]
    matchHosts: [api.example.com]
    matchPorts: ["443"]
    policy: GATEWAY
    gateway:
      service: agentio-egress.agentio-system.svc.cluster.local
      port: 15008
  - namespaces: [agent-demo]
    policy: PASSTHROUGH
```

To reject a destination, create a separate TrafficPolicy in the source workload namespace. This policy applies to all workloads in `agent-demo`; add a selector to narrow its scope. The final allow rule preserves access to other destinations.

```yaml
apiVersion: agents.kruise.io/v1alpha1
kind: TrafficPolicy
metadata:
  name: reject-blocked-host
  namespace: agent-demo
spec:
  selector: {}
  egress:
    rules:
      - action: reject
        to:
          - fqdn: blocked.example.com
      - action: allow
        to:
          - cidr: 0.0.0.0/0
```

Legacy egress DENY may combine ordering with routing decisions. Review the effective access-control behavior when migrating overlapping rules; replacing an action without considering precedence is not a general translation.

## External processing provider

An `ExtProcProvider` can be set globally at `sandboxExtProc`, in `additionalExtProcs`, or per gateway at `egressGateways[].extProc`.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `name` | String | Empty | Required, unique DNS label for each additional processor; ignored for the primary provider. Identifies filters, clusters, and statistics independently of list position. |
| `service` | String | Empty | DNS hostname or address of the gRPC processor. Used when `serviceRef` is absent. Additional processors require `service` or `serviceRef`. |
| `serviceRef` | Service reference | Unset | Kubernetes Service identified by required `namespace` and `name`. Takes precedence over `service` and selects endpoint discovery. |
| `port` | Integer | `9002` | Service port. With `serviceRef`, mapped to the Service's actual endpoint port. |
| `request.headerMode` | Enum | `SEND` | `DEFAULT`, `SEND`, or `SKIP` for request headers and trailers. `DEFAULT` uses Agentio's request default. |
| `request.attributes` | `string[]` | Empty | Envoy attributes included with request processing messages. |
| `response.headerMode` | Enum | `SKIP` | `DEFAULT`, `SEND`, or `SKIP` for response headers and trailers. `DEFAULT` uses Agentio's response default. |
| `response.attributes` | `string[]` | Empty | Envoy attributes included with response processing messages. |
| `failureModeAllow` | Boolean | `false` | Continue traffic when the processor is unavailable or returns an error. When `false`, processor failures fail closed. |
| `messageTimeout` | String | `200ms` | Timeout for each processing message, expressed as a Go duration string. |
| `clusterSettings.http.maxConcurrentStreams` | Integer | `1024` (Envoy default) | Maximum concurrent HTTP/2 streams per upstream connection. Agentio leaves the field unset when configured as `0`. |
| `clusterSettings.http.maxRequestsPerConnection` | Integer | `0` | Maximum requests before closing an upstream connection. `0` means unlimited. |

If an egress gateway has no `extProc` field, it inherits `sandboxExtProc`. A gateway-level provider replaces the global provider. A gateway-level `extProc: {}` has neither `service` nor `serviceRef` and disables external processing for that gateway.

Use `serviceRef` for a Kubernetes Service whose Pod endpoints should be pushed to gateways:

```yaml
sandboxExtProc:
  service: agentio-epe.agentio-system.svc.cluster.local
  serviceRef:
    namespace: agentio-system
    name: agentio-epe
  port: 9002
```

The reference always identifies a Service, including a headless Service. `service` and `serviceRef` may coexist during migration: controllers that support `serviceRef` use endpoint discovery, while older controllers ignore the unknown reference and use `service`. TLS and HTTP/2 settings apply to both discovery methods.

The chart generates `sandboxExtProc` automatically when `epe.mode` is `managed` or `external`. Its generated `messageTimeout` is `5s`, rather than the raw API default of `200ms`; set `epe.messageTimeout` or use `agentiod.config.values.sandboxExtProc` to override it.

Managed mode generates both `service` and `serviceRef`, using the actual EPE Service name and release namespace. External mode defaults to DNS; set `agentiod.config.values.sandboxExtProc.serviceRef` to reference an external processor's Kubernetes Service. To force DNS in managed mode, explicitly set `agentiod.config.values.sandboxExtProc.serviceRef: null`; changing `service` alone does not override a generated reference.

See [EPE configuration](epe-configuration.md) for the deployed EPE service, listeners, Helm values, and process settings.

## Additional external processors

Configure trusted processors after the default EPE without replacing it:

```yaml
additionalExtProcs:
- name: policy
  service: policy.extensions.svc.cluster.local
  port: 9002
  messageTimeout: 200ms
  failureModeAllow: false
- name: transform
  service: transform.extensions.svc.cluster.local
  port: 9002
  response:
    headerMode: SEND
```

Requests run through the effective primary provider, then each additional processor in order. Responses run in reverse order. The list applies to inspected HTTP, including HTTP after gateway TLS termination; it does not apply to CONNECT setup, raw TCP, or TLS passthrough. A gateway-level primary override still uses the global list; `extProc: {}` disables the entire chain for that gateway. With no effective primary provider, additional processors are inactive.

Each entry reuses the provider's timeout, failure mode, TLS, connection pool, and processing attributes. Names must be unique lowercase DNS labels (up to 63 characters). Services must be nonempty, ports are 1–65535 (`0` selects 9002), and an explicit message timeout must be positive. Changing the order, endpoints, or options updates the gateway configuration without restarting gateway Pods. Supplying `additionalExtProcs: []` removes the list; an omitted or null list preserves the lower configuration layer.

Additional processors see mutations already committed by EPE, including any injected credentials, and may modify that request further. Their decisions do not re-enter EPE policy evaluation. Only grant this capability to trusted services.

## Egress gateway settings

Each entry in `egressGateways` matches a running gateway by verified workload identity: `name` must equal its ServiceAccount name and `namespace` must match exactly. The same rule applies to gateways registered through Gateway API. Pod-bound token and active-Pod checks still apply.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `name` | String | Empty | Gateway name and expected ServiceAccount name. |
| `namespace` | String | Empty | Namespace of the gateway workload. Gateways may run outside `agentio-system`. |
| `tlsTermination.includeHosts` | `string[]` | Empty | SNI host patterns selected for TLS termination. Wildcards such as `*.example.com` are supported. On-demand certificate issuance is authorized by gateway identity, not by this list. |
| `tlsTermination.excludeHosts` | `string[]` | Empty | SNI host patterns forwarded without TLS termination. Wildcards are supported. In static SNI matching, an identical pattern in both lists belongs to `excludeHosts` (case-insensitive); repeated patterns are registered once. Different overlapping patterns retain Envoy's most-specific-match precedence. |
| `extProc` | `ExtProcProvider` | Inherit global | Per-gateway external-processing override. An explicitly empty provider disables it for this gateway. |
| `tls.origination` | `UpstreamTlsSettings` | TLS 1.2–1.3 and eight cipher suites | Per-gateway upstream TLS defaults and overrides; see below. |
| `upstreamTrustBundle` | `UpstreamTrustBundle` | Built-in public CA package | Additional CA sources for destination and HTTPS proxy TLS verification. |
| `http.acceptHttp10` | Boolean | `true` | Accept HTTP/1.0 on business HTTP listeners; explicitly `false` rejects it. |
| `http` | `GatewayHttpSettings` | See below | Business HTTP protocol, stream timeout, and routing settings. |
| `tcp` | `TcpSettings` | See below | TCP forwarding connection timeouts, including the TLS termination relay. |
| `tcpPassthrough` | `TcpPassthroughMatch[]` | Empty | Forward matching original destination CIDRs/ports as TCP without HTTP/TLS inspection. |
| `connectRateLimit` | `LocalRateLimitSettings` | Unset | Local token-bucket limit for new HTTP/2 CONNECT streams. |
| `connectConcurrencyLimit` | `ConnectConcurrencyLimitSettings` | Unset | Shared limits on active TCP CONNECT streams, grouped by trusted filter state. |
| `bandwidthLimit` | `BandwidthLimitSettings` | Unset | Per-filter-state TCP byte shaping on CONNECT, shared across connections and workers in one gateway process. |
| `serviceEntries` | `EgressServiceEntry[]` | Empty | Endpoint IPs and allowed host identities. Envoy retains a matching original destination without resolving its hostname again. |
| `accessLogFormat` | `AccessLogFormat` | Built-in JSON | Format of the built-in `envoy` access-log provider on stdout for this gateway. See below. |

### TCP passthrough

Use `egressGateways[].tcpPassthrough` for database connections, custom protocols,
or server-first protocols that must connect upstream before sending client data.
Matching connections go directly to the original CONNECT destination as TCP.
The gateway does not inspect HTTP/TLS, terminate application TLS, resolve SNI/Host,
or execute SecurityProfile application rules on this path.

```yaml
egressGateways:
- name: agentio-egress
  namespace: agentio-system
  tcpPassthrough:
  - cidrs: ["10.20.0.0/16"]
    ports: [3306, 5432]
  - cidrs: ["192.168.10.20/32"]
  - ports: [6379]
```

Entries are ORed. Within an entry, CIDRs and ports are ANDed; values within each
list are ORed. CIDRs match the original destination IPv4/IPv6 address without DNS.
The first matching entry selects passthrough; all entries use the same forwarding
behavior, so their order does not change which destinations bypass inspection.
CIDRs with host bits are normalized to their network prefix (`10.20.1.2/16` matches
`10.20.0.0/16`).
An omitted dimension matches any value; an empty entry (`{}`) selects all TCP
connections. An omitted or empty `tcpPassthrough` list preserves existing inspection.
The setting applies to every workload using this gateway and is also available in
the Gateway API parametersRef configuration.

TCP passthrough selects processing, not permission: Sandbox-side TrafficPolicy,
CONNECT identity checks, admission limits, TCP timeouts and access logging remain
in effect.

### HTTP protocol

Business HTTP listeners accept HTTP/1.0 by default, both for plaintext traffic and HTTP after TLS termination. Set `egressGateways[].http.acceptHttp10: false` to reject HTTP/1.0 on a particular gateway:

```yaml
egressGateways:
- name: agentio-egress
  namespace: agentio-system
  http:
    acceptHttp10: false
```

Omitting `http`, using `http: {}`, or setting `acceptHttp10: true` enables HTTP/1.0. Requests still require a valid authority, supplied by a `Host` header or extracted from an absolute request URL; no default host is configured. This setting also applies to Gateway API `parametersRef` configuration. It does not change the outer HTTP/2 CONNECT tunnel or TLS passthrough traffic. Preserve other gateway entries and settings when updating the `egressGateways` list.

Envoy gateways preserve an upstream `Server` response header and do not add one when it is absent. The router also suppresses its generated `x-envoy-*` headers, including `x-envoy-upstream-service-time`. Headers supplied by upstream services or external processors are passed through.

The protocol names used in access-log expressions and CEL filters are listed in [Gateway protocol names](../design/gateway-protocol-names.md).

### Access-log format

Set `egressGateways[].accessLogFormat` in AgentioConfig to customize a gateway's access logs. Choose either `json` for a JSON object or `text` for a text template. Both support [Envoy access-log substitution operators](https://www.envoyproxy.io/docs/envoy/latest/configuration/observability/access_log/usage). The format applies to HTTP and TCP logs, CONNECT failures, listener filter-chain misses, and SNI denials when SNI policy enforcement is enabled. The TLS-termination relay itself does not emit duplicate application logs.

For example, put this AgentioConfig fragment in the `data.config` of `agentio-config` or `agentio-config-primary`. With Helm, put the same fragment under `agentiod.config.values`. Preserve the other gateway entries and settings when updating the list, because `egressGateways` uses list replacement semantics.

```yaml
egressGateways:
- name: agentio-egress
  namespace: agentio-system
  accessLogFormat:
    json:
      start_time: "%START_TIME%"
      scheme: "%REQ(:SCHEME)%"
      protocol: "%PROTOCOL%"
      authority: "%REQ(:AUTHORITY)%"
      requested_server_name: "%CEL('agentio.tls.outer_sni' in filter_state ? filter_state['agentio.tls.outer_sni'] : connection.requested_server_name)%"
      upstream_address: "%UPSTREAM_REMOTE_ADDRESS%"
      response_code: "%RESPONSE_CODE%"
      denial_reason: "%FILTER_STATE(agentio.egress.denial_reason:PLAIN)%"
```

The JSON object replaces the complete default format; its fields are not merged with the defaults. Nested objects and typed values are supported. Unavailable JSON values may be omitted or appear as `null`; log consumers should accept both. This example's illustrative output after HTTPS termination is:

```json
{"start_time":"2026-09-11T10:00:00.000Z","scheme":"https","protocol":"HTTP/2","authority":"api.example.com","requested_server_name":"api.example.com","upstream_address":"203.0.113.10:443","response_code":200,"denial_reason":null}
```

`scheme` distinguishes HTTP from terminated HTTPS; `protocol` is the HTTP version. The SNI expression preserves the original ClientHello name after TLS termination and falls back to the current connection's SNI for passthrough TLS. HTTP authority remains a separate field. TCP logs have no HTTP scheme or request headers.

The default format includes `denial_reason: "sni_policy_denied"` for connections rejected by SNI policy, `"tcp_policy_denied"` when TLS falls through to a rejecting TCP rule, and `"service_entry_denied"` for ServiceEntry TLS identity mismatches or unsupported opaque TCP. The native connection-policy module reports missing, unavailable, or invalid policies as `"connection_policy_missing"`, `"connection_policy_unavailable"`, or `"connection_policy_invalid"`. These connections close directly without an upstream connection or application response. Listener access logs preserve the captured reason using the configured TCP log provider, format, and filter. HTTP errors and connection failures continue to use their existing response and transport fields. Custom formats can retain the reason with the `denial_reason` entry shown above.

TCP denial logs report `response_code_details: "direct_response"` instead of an upstream failure and have no upstream cluster or address. The old deny TCP proxy counters and `BlackHoleCluster` are no longer generated; use `denial_reason` to identify policy rejections.

Internal upstream cluster and filter-chain names are omitted from the default format. For debugging, add these entries to your custom `accessLogFormat.json` object:

```yaml
upstream_cluster: "%UPSTREAM_CLUSTER%"
filter_chain: "%FILTER_CHAIN_NAME%"
```

To use text output instead, replace `accessLogFormat` with:

```yaml
accessLogFormat:
  text: |
    [%START_TIME%] %REQ(:SCHEME)% %REQ(:METHOD)% %REQ(:AUTHORITY)% %PROTOCOL% %RESPONSE_CODE% upstream=%UPSTREAM_REMOTE_ADDRESS%
```

Agentio appends a trailing newline if it is missing. Unavailable values in text output use Envoy's `-` placeholder. Do not set `text` and `json` together; blank text and an empty `json` object are rejected. Omitting `accessLogFormat` or setting it to `{}` restores the built-in JSON format.

ConfigMap updates take effect without restarting `agentiod` or the gateway. Formatting is scoped to the configured gateway. Telemetry still controls whether the logs are enabled and which requests are logged, including the existing CONNECT and listener failure filters. Gateway API `parametersRef` ConfigMaps accept the same `accessLogFormat` field.

Agentio validates the configuration structure; Envoy validates substitution operators and CEL expressions when it receives the configuration. An unsupported operator or malformed expression can cause Envoy to reject the listener update.

### TLS termination for HTTPS inspection

An HTTPS connection reaches gateway HTTP filters such as EPE only when its SNI host is selected for TLS termination. A routed HTTPS connection that is not terminated stays on the TCP forwarding chain and bypasses request-level `SecurityProfile` evaluation.

Native Envoy gateways resolve the actual ClientHello SNI for TLS passthrough and connect to that name on the original destination port. They do not fall back to the original destination IP when SNI is absent or resolution fails. The gateway's DNS destination restrictions apply to this resolution. TLS passthrough preserves the client's TLS handshake; it does not create an additional upstream TLS layer.

Native gateways reject malformed SNI hostnames, including names containing a port, before selecting a TLS filter chain. This check also applies to excluded hosts and when SNI traffic policy is disabled, so SNI cannot override the original destination port.

After TLS termination, non-HTTP TCP payloads and application-level CONNECT requests use the saved outer SNI to resolve the upstream destination and verify its certificate, retaining the original destination port. Nested TLS or an inner CONNECT authority cannot select a different outer destination. HTTP requests continue to require an authority consistent with the outer SNI. Matching `serviceEntries` preserve the explicitly bound original endpoint instead of resolving SNI again, including TLS passthrough and post-termination forwarding. Legacy proxyv2 gateways retain their existing forwarding behavior during upgrades.

Configure all three parts of the trust boundary:

1. Add each inspected hostname to the `tlsTermination.includeHosts` of the `egressGateways` entry whose `name` and `namespace` match the gateway ServiceAccount.
2. Configure the MITM signing CA. For production, select `SECRET` mode and provide a Secret containing `ca.crt` and `ca.key`; the default `SELF_SIGN` mode maintains a control-plane-managed CA in a Secret.
3. Configure calling workloads to trust the MITM CA. Set `agentiod.injector.clientTrust.enabled: true` to combine and distribute public CAs with the MITM trust bundle and inject Python/Node.js/curl trust environment variables into newly created business containers. This master switch defaults to disabled and is independent of the data-plane profile. Namespace and Pod labels `client-trust.agentio.kruise.io/inject: "true"` enable CA injection into workloads without a sidecar; Pod labels take precedence. Ambient installations use CA-only admission. See [client CA trust](../tasks/configure-client-ca-trust.md) for container selection, overrides, custom sources and the rollout required for existing Pods, and the [Istio integration guide](../integrations/istio-ambient.md) for using an existing mesh. Clients that do not read the injected environment variables need their own trust configuration. Do not disable certificate verification as a production workaround.

For example, after creating `agentio-mitm-ca` in `agentio-system` from an operator-managed CA, these values enable inspection of two hosts:

```yaml
agentiod:
  mitm:
    signMode: SECRET
    secretNamespace: agentio-system
    secretName: agentio-mitm-ca
  config:
    values:
      egressGateways:
        - name: agentio-egress
          namespace: agentio-system
          tlsTermination:
            includeHosts:
              - api.example.com
              - mcp.example.com
```

The Secret coordinates and gateway namespace must be consistent. See [MITM certificate environment variables](agentiod-environment-variables.md#on-demand-tls-certificates) for the complete signing settings.

### Upstream CA trust

Use `upstreamTrustBundle.additionalSources` to trust private CAs while retaining the built-in public CA package. Each entry must select exactly one `configMapRef` or `secretRef`, with an explicit `name` and `key`. Both kinds are resolved in the **mesh root namespace**, even when the gateway is declared in another namespace. References do not accept a `namespace` field.

For example, create these sources in `agentio-system` when that is the root namespace:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: company-ca
  namespace: agentio-system
data:
  ca.crt: |
    <COMPANY_CA_CERTIFICATES_PEM>
---
apiVersion: v1
kind: Secret
metadata:
  name: partner-ca
  namespace: agentio-system
type: Opaque
stringData:
  ca.crt: |
    <PARTNER_CA_CERTIFICATES_PEM>
```

Reference them from the gateway configuration:

```yaml
egressGateways:
  - name: egress-gateway
    namespace: sandbox-traffic-system
    upstreamTrustBundle:
      additionalSources:
        - configMapRef:
            name: company-ca
            key: ca.crt
        - secretRef:
            name: partner-ca
            key: ca.crt
```

Each selected key must contain one or more PEM CA certificates; private keys, non-CA service certificates, empty sources, and malformed PEM are rejected. ConfigMaps use `data`; Secrets use `data` (or `stringData` when creating them). The controller merges and deduplicates these certificates with the built-in public CA package and sends the complete bundle to both destination and HTTPS proxy TLS origination clusters. Hostname verification remains enabled. This does not change the workload `clientTrustBundle` or the MITM signing CA.

Source updates apply without restarting `agentiod` or the gateway. If a source is missing, its selected key is absent, or its contents are invalid, compilation reports the gateway, source, key, and reason and retains the previous valid gateway output. An initially invalid configuration produces no gateway resources. Check compiler failures before relying on a trust change having taken effect.

Remove entries, or set `additionalSources: []`, to remove their contribution. A CA remains trusted if it is still present in another source or the public package. Existing TLS connections can remain active until they close.

`agentiod` always loads the public CA package at startup. Standard images provide it at `/usr/local/share/agentio/trust-package/cert-manager-package-debian.json`; set `AGENTIO_CLIENT_TRUST_PACKAGE_PATH` only to override this path. An empty path or an unreadable or invalid package prevents startup.

Gateway API `parametersRef` ConfigMaps accept the same `upstreamTrustBundle` block in `data.config`, without the `egressGateways` wrapper. Trust sources still resolve in the mesh root namespace, independently of the parameters ConfigMap namespace.

### Upstream TLS defaults

When the sandbox egress gateway originates TLS to a destination or an HTTPS proxy, it explicitly allows TLS 1.2 through TLS 1.3. Its TLS 1.2 cipher list contains the six ECDHE AES-GCM and ChaCha20-Poly1305 suites, followed by `AES128-GCM-SHA256` and `AES256-GCM-SHA384` for older public servers without ECDHE support. Connections negotiating these two RSA suites do not provide forward secrecy. TLS 1.3 cipher suites are managed separately by Envoy.

Upstream CA and hostname verification remain enabled. Session resumption is disabled for EPE mTLS and downstream TLS termination. These settings do not change connections forwarded without termination.

Override the upstream defaults per gateway with `tls.origination`:

```yaml
agentiod:
  config:
    values:
      egressGateways:
      - name: agentio-egress
        namespace: agentio-system
        tls:
          origination:
            minProtocolVersion: TLSV1_2
            maxProtocolVersion: TLSV1_3
            cipherSuites:
            - ECDHE-ECDSA-AES128-GCM-SHA256
            - ECDHE-RSA-AES128-GCM-SHA256
            - ECDHE-ECDSA-AES256-GCM-SHA384
            - ECDHE-RSA-AES256-GCM-SHA384
            - ECDHE-ECDSA-CHACHA20-POLY1305
            - ECDHE-RSA-CHACHA20-POLY1305
```

This example removes RSA key-exchange suites. For a raw ConfigMap `data.config`, start at `egressGateways` without the Helm `agentiod.config.values` wrapper. Preserve the other gateway fields and gateway entries when replacing the list.

| Field | Default | Behavior |
| --- | --- | --- |
| `minProtocolVersion` | `TLSV1_2` | Accepts `DEFAULT`, `TLSV1_2`, or `TLSV1_3`. |
| `maxProtocolVersion` | `TLSV1_3` | Same values; cannot be below the effective minimum. |
| `cipherSuites` | Eight suites described above | A non-empty list replaces the default list in order; omitted or empty lists restore defaults. Only affects TLS 1.2. |

`DEFAULT` or an omitted version uses that field's default. Set only `maxProtocolVersion: TLSV1_2` for TLS 1.2 only, or only `minProtocolVersion: TLSV1_3` for TLS 1.3 only. Cipher names must be explicit Envoy/OpenSSL names recognized by the controller; unknown names, expressions such as `ALL`, and duplicates are rejected. Invalid settings reject the configuration layer.

The override applies to both destination and HTTPS proxy TLS origination on the matching gateway. CA verification, hostname verification, and session cache behavior cannot be disabled through this API. Domain-specific TLS overrides are not currently supported; `tlsTermination.excludeHosts` selects TLS passthrough.

Gateway API `parametersRef` ConfigMaps accept the same `tls.origination` block in `data.config`, alongside `tlsTermination`, without an `egressGateways` wrapper or embedded gateway name and namespace.

### HTTP routing and TCP timeouts

All paths below are relative to an `egressGateways[]` entry. `http.routing.fallback` applies only when no host override matches; overrides replace the complete timeout/retry policy and do not inherit missing fields from the fallback. An override for `*` replaces the fallback policy.

| Field | Default | Description |
| --- | --- | --- |
| `tcp.idleTimeout` | `1h` | Closes an idle TCP connection. |
| `tcp.maxConnectionDuration` | Unset | Absolute lifetime of a downstream TCP connection. |
| `http.streamIdleTimeout` | `30m` | Closes an idle HTTP stream, including WebSocket and server-sent event streams. |
| `http.routing.fallback.timeout` | `0s` | Total timeout for the fallback route. `0s` disables the timeout. |
| `http.routing.fallback.retries` | Unset | Retry policy using Istio's [`HTTPRetry`](https://istio.io/latest/docs/reference/config/networking/virtual-service/#HTTPRetry) fields. |
| `http.routing.hostOverrides[].hosts` | Empty | Exact or wildcard destination host patterns, matched independently of the request port. `*` overrides the default route settings; duplicate patterns across or within overrides are rejected case-insensitively. |
| `http.routing.hostOverrides[].settings` | Unset | `timeout` and `retries` applied to the matching hosts. |

### CONNECT rate limiting

Each accepted HTTP/2 CONNECT stream consumes one token.

Use the same `rateLimits[].actions[]` and `descriptors[].entries[]` grouping format as concurrency and bandwidth limits. `filterState` reads a trusted string value; `genericKey` supplies a fixed value. Each action group produces a separate ordered descriptor, so sandbox and gateway-wide limits can apply together:

```yaml
connectRateLimit:
  rateLimits:
    - actions:
        - filterState: {key: agentio.sandbox.id, descriptorKey: sandbox}
    - actions:
        - genericKey: {descriptorKey: scope, descriptorValue: gateway}
  descriptors:
    - entries: [{key: sandbox}]
      tokenBucket: {maxTokens: 10, tokensPerFill: 2, fillInterval: 1s}
    - entries: [{key: scope, value: gateway}]
      tokenBucket: {maxTokens: 100, tokensPerFill: 20, fillInterval: 1s}
```

Only the configuration grouping is shared: CONNECT rate limiting still uses Envoy's native local rate limit filter, including its matching and bucket lifecycle. Supply identity in a preceding trusted filter. Legacy `entries[].cel` configurations remain accepted when `rateLimits` is omitted; combining the two forms is rejected.

Burst is already supported through `maxTokens`: for example, `maxTokens: 100`, `tokensPerFill: 10`, `fillInterval: 1s` permits an initial burst of 100 attempts and replenishes 10 tokens per second. No separate burst field is needed. Keep `perDownstreamConnection: false` for a shared gateway budget.

| Field | Default | Description |
| --- | --- | --- |
| `rateLimits[].actions[]` | Unset | Ordered `filterState` / `genericKey` sources, using the same format as bandwidth and concurrency. Multiple groups generate separate descriptors. |
| `tokenBucket` | Unset | Optional gateway-wide bucket, charged in addition to matching descriptor buckets. Retained as a shorthand; a fixed `genericKey` group can express the gateway total instead. |
| `tokenBucket.maxTokens` | `0` | Bucket capacity and initial token count. |
| `tokenBucket.tokensPerFill` | `1` | Tokens added on each fill interval when omitted or zero. |
| `tokenBucket.fillInterval` | Unset | Refill interval; it must be at least `50ms`. |
| `descriptors[]` | Empty | Descriptor-specific token buckets. Entry keys/order must match an action group when `rateLimits` is configured. Matching follows the native Envoy filter. |
| `descriptors[].entries[].key` | Empty | Descriptor key. |
| `descriptors[].entries[].value` | Empty | Exact value. Empty acts as a wildcard and creates a bucket for each distinct runtime value. |
| `descriptors[].entries[].cel` | Empty | Legacy CEL value source, supported only when `rateLimits` is omitted. In this form, each descriptor generates its own ordered action group; entries without CEL use their non-empty `value` as a constant. |
| `descriptors[].tokenBucket` | Unset | Bucket used by the matching descriptor. |
| `perDownstreamConnection` | `false` | Creates a token bucket for each ztunnel-to-gateway connection. It cannot be combined with wildcard descriptor values. |

### CONNECT concurrency limits

`egressGateways[].connectConcurrencyLimit` limits **active TCP CONNECT streams**, including upstream connection establishment. It is independent of `connectRateLimit` (new-stream rate) and `bandwidthLimit` (payload byte rate). All three can be enabled together.

```yaml
connectConcurrencyLimit:
  rateLimits:
    - actions:
        - filterState: {key: agentio.sandbox.id, descriptorKey: sandbox}
    - actions:
        - genericKey: {descriptorKey: scope, descriptorValue: gateway}
  descriptors:
    - entries: [{key: sandbox}]
      maxConcurrentStreams: 64
    - entries: [{key: scope, value: gateway}]
      maxConcurrentStreams: 4096
```

These numbers are examples, not capacity recommendations. Use a globally unique sandbox identity, or combine tenant and sandbox actions/entries.

| Field | Default | Meaning |
| --- | --- | --- |
| `rateLimits[].actions[]` | Required | Ordered `filterState` / `genericKey` sources, as for bandwidth limits. |
| `descriptors[].entries[]` | Required | Ordered entries matching an action group. An empty `value` creates a distinct bucket for each runtime value. |
| `descriptors[].maxConcurrentStreams` | Required | Positive active-stream limit for each matched key. |
| `maxDynamicBuckets` | `10000` | Maximum live wildcard-derived counters; exact descriptors do not consume this capacity. |

Behavior:

- All matching groups must have room; their counters are acquired together.
- Quota exhaustion is rejected rather than queued. A full stream quota returns 429; exhausted distinct-key capacity returns 503; missing required identity returns 403.
- Slots are held from admission until stream destruction.
- **Lowering a limit does not evict existing streams; it blocks new admission until the count is below the new limit.**
- Removing the setting disables admission control on existing instances and stops creating instances for new streams.
- Limits are per gateway process, not pooled across replicas.

Upgrade all gateway instances before enabling these limits; streams created while the limit was absent are not counted retroactively.

### CONNECT bandwidth limits

`egressGateways[].bandwidthLimit` limits the TCP payload carried by CONNECT. HTTP, TLS records, and other TCP payloads count toward the same budget; outer tunneling and TLS overhead do not. `connectRateLimit` continues to count **new CONNECT streams**; `bandwidthLimit` counts **bytes** and delays transmission with backpressure. Both settings can be enabled together.

```yaml
egressGateways:
  - name: agentio-egress
    namespace: agentio-system
    bandwidthLimit:
      rateLimits:
        - actions:
            - filterState:
                key: agentio.sandbox.id
                descriptorKey: sandbox
      descriptors:
        - entries:
            - key: sandbox
          bandwidthLimit:
            uploadBytesPerSecond: 10485760
            downloadBytesPerSecond: 52428800
            uploadBurstBytes: 1048576
            downloadBurstBytes: 5242880
```

Merge this fragment into the existing `data.config` or Helm `agentiod.config.values`; `egressGateways` uses list replacement, so preserve other entries and settings.

| Field | Default | Meaning |
| --- | --- | --- |
| `rateLimits[].actions[]` | Required | Ordered sources forming one composite descriptor. Multiple groups can enforce multiple budgets together. |
| `actions[].filterState.key` | Required for this source | Trusted filter state serialized as a nonempty UTF-8 string. |
| `actions[].filterState.descriptorKey` | Required for this source | Output descriptor key, unique within its group. |
| `actions[].genericKey` | Unset | Alternative fixed source with nonempty `descriptorKey` and `descriptorValue`. Each action specifies exactly one source. |
| `descriptors[].entries[]` | Required | Ordered `key`/`value` entries matching a complete action group. Empty or omitted `value` creates a distinct bucket for each actual value combination. |
| `descriptors[].bandwidthLimit.uploadBytesPerSecond` | Unlimited | Positive bytes/second from downstream to upstream. |
| `descriptors[].bandwidthLimit.downloadBytesPerSecond` | Unlimited | Positive bytes/second from upstream to downstream. At least one direction is required. |
| `descriptors[].bandwidthLimit.uploadBurstBytes` | One-batch pacing | Positive upload burst capacity in bytes; requires `uploadBytesPerSecond`. |
| `descriptors[].bandwidthLimit.downloadBurstBytes` | One-batch pacing | Positive download burst capacity in bytes; requires `downloadBytesPerSecond`. |
| `maxDynamicBuckets` | `10000` | Maximum wildcard-derived buckets per gateway process. |
| `bufferLimitBytes` | `65536` | Soft streaming watermark per stream. |

Behavior:

- All connections and workers matching a descriptor share its budget; reconnecting does not reset it.
- **Burst bytes are not a strict wire-level burst cap:** a callback batch larger than the burst capacity can exceed it. The whole batch is charged, and subsequent traffic waits for the outstanding debt, including after reconnecting.
- The native gateway's one-second internal protocol inspection deadline excludes bandwidth pacing waits. Silent clients still time out; increasing `listener_filters_timeout` with a GatewayPatch is unnecessary and reintroduces a wall-clock limit on queued connections.
- A complete exact descriptor takes precedence over wildcards; otherwise the first matching wildcard wins. Multiple matching action groups charge their budgets together.
- Missing required identity returns 403; a complete unmatched descriptor is unlimited; a new key exceeding dynamic capacity returns 503.
- Lowering capacity retains existing buckets but blocks new keys until space is available.
- **Router retries are unsupported on the bandwidth-shaped CONNECT chain;** do not add retry policies at the route or virtual-host level through patches.
- Removing the setting disables pacing on existing instances and stops creating instances for new streams.
- Limits are per gateway process, not pooled across replicas.

### Static service entries

For Envoy-backed gateways, a `serviceEntries` entry binds allowed host identities to endpoint IP addresses. The gateway matches the original destination IP restored from HBONE. For a matching IP, it validates HTTP Host / `:authority` or TLS SNI against the corresponding hosts, then retains the original IP and port without resolving the hostname again. This supports Pods using `hostAliases`: the Pod selects the endpoint, and the gateway keeps that choice.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `hosts` | `string[]` | Empty | Exact FQDNs matched against the HTTP Host / `:authority` and TLS SNI identities. Wildcards are not supported. At least one host is required, and a host must not repeat across the `serviceEntries` of one gateway. |
| `endpoints[].address` | String | Empty | IPv4 address matched against the original destination. At least one endpoint is required, and addresses must be unique within one entry. The client-selected endpoint is preserved. If several entries share an IP, their allowed hosts are combined. |

Host validation and target capture occur before EPE processing. When EPE target authorization is enabled, EPE checks the original endpoint against TrafficPolicy without DNS. A denied endpoint returns HTTP 403 without trying another endpoint or DNS. Endpoint matching does not authorize a request by itself.

An IP match with an unrelated HTTP Host returns HTTP 403. An unrelated or absent TLS SNI closes the connection. These failures do not fall back to normal forwarding. Opaque TCP addressed to a configured endpoint is rejected because it has no HTTP Host or TLS SNI to validate. If the IP does not match any entry, ordinary forwarding and authorization apply; a matching hostname alone does not select a static endpoint.

For enforcement, keep the EPE provider's request header mode as `SEND` (the default) and `failureModeAllow: false`. Upgrade the gateway and EPE together: an older gateway does not supply the ServiceEntry candidate, and an older EPE does not authorize it.

Entries cover ordinary HTTP, decrypted HTTPS, and TLS passthrough. SNI validation does not bypass the existing TLS termination/passthrough/deny policy. Passthrough cannot inspect the encrypted HTTP Host; terminate TLS if Host/SNI consistency must also be enforced. Application-level CONNECT requests retain their separate upstream-proxy route and do not capture a ServiceEntry target; when carried over TLS, the outer SNI is still checked against the proxy's endpoint binding.

Hosts are normalized to lowercase without a trailing dot; requests accept equivalent case and a trailing dot. Timeout and retry settings continue to follow the ordinary [HTTP routing rules](#http-routing-and-tcp-timeouts). An invalid entry — an empty host or endpoint list, a non-IPv4 address, a wildcard or duplicate host — rejects that configuration layer.

**Migration:** Envoy no longer selects or balances static endpoints by HTTP Host. Configure application DNS or `hostAliases` to send traffic to one of the declared endpoint IPs. The separate [agentgateway backend](../tasks/deploy-agentgateway.md) retains its documented host-based static routing behavior.

```yaml
egressGateways:
  - name: agentio-egress
    namespace: agentio-system
    serviceEntries:
      - hosts:
          - api.example.com
        endpoints:
          - address: 203.0.113.10
          - address: 203.0.113.11
```

## Gateway configuration migration

The gateway configuration is grouped by protocol. The old fields are removed; update the complete gateway entries in both AgentioConfig sources and Gateway API `parametersRef` ConfigMaps:

| Removed path | New path |
| --- | --- |
| `connectionPool.tcp` | `tcp` |
| `connectionPool.http.streamIdleTimeout` | `http.streamIdleTimeout` |
| `connectionPool.http.defaultRoute` | `http.routing.fallback` |
| `connectionPool.http.routeOverrides` | `http.routing.hostOverrides` |
| `upstreamTls` | `tls.origination` |

`tlsTermination` retains its location, fields, and behavior. The moved timeout, retry, and TLS settings retain their defaults and matching semantics. HTTP/1.0 is now enabled by default; set `http.acceptHttp10: false` to disable it. Both values route HTTP/1.0 through the HTTP filter chain; disabling it rejects the request instead of forwarding it as opaque TCP.

Old paths are not aliases. AgentioConfig ignores them with a warning, so their settings do not take effect. Gateway API `parametersRef` payloads reject unknown fields, including these old paths. Migrate both sources when deploying the new control plane. Invalid updates retain the last effective configuration; retained configuration does not survive a process restart. External processor `clusterSettings` and EPE HTTP-callout `connectionPool` settings are separate APIs and are unchanged.

## Inspect configuration sources

Always inspect both ConfigMaps when debugging effective behavior:

```console
$ kubectl get configmap \
    agentio-config agentio-config-primary \
    --namespace agentio-system \
    --ignore-not-found \
    --output yaml
```

If `agentio-config-primary` contains the field you are troubleshooting, it takes precedence even after a successful `helm upgrade` changes `agentio-config`.

Inspect controller logs for parsing or application failures:

```console
$ kubectl logs deployment/agentiod \
    --namespace agentio-system \
  | grep -i 'agentio config'
```
