# Customize Gateway resources

Use `Gateway.spec.infrastructure.parametersRef` to customize the Kubernetes resources generated by Agentio's gateway deployer. Enable `egressGateway.mode: gatewayAPI` and install the Gateway API CRDs first; see [Route traffic through an egress gateway](route-traffic-through-egress-gateway.md).

## Patch a Gateway

Reference a core ConfigMap in the same namespace as the Gateway:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: egress
  namespace: demo
spec:
  gatewayClassName: agentio-egress
  infrastructure:
    parametersRef:
      group: ""
      kind: ConfigMap
      name: egress-parameters
  listeners:
  - name: hbone
    port: 15008
    protocol: HBONE
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: egress-parameters
  namespace: demo
data:
  deployment: |
    spec:
      template:
        spec:
          containers:
          - name: agentio-proxy
            resources:
              requests:
                cpu: 250m
                memory: 256Mi
            env:
            - name: EXAMPLE_SETTING
              value: enabled
  service: |
    spec:
      type: ClusterIP
```

Each key contains a Strategic Merge Patch applied after template rendering:

| ConfigMap data key | Resource |
| --- | --- |
| `deployment` | Deployment |
| `service` | Service |
| `serviceAccount` | ServiceAccount |
| `horizontalPodAutoscaler` | HorizontalPodAutoscaler |
| `podDisruptionBudget` | PodDisruptionBudget |

Containers and environment variables merge by `name`; a container entry with a new name adds a sidecar. Use `agentio-proxy` for the Envoy gateway and `agentgateway` for the native agentgateway. Strategic Merge Patch directives such as `$patch: delete` are supported. Patches may modify labels and annotations, but may not change resource identity or ownership metadata, such as name, namespace, owner references, or finalizers.

Generated gateway Services have no topology preference by default. To prefer nearby gateway replicas, set `spec.trafficDistribution: PreferClose` in a `service` patch on clusters that support the field. Agentio translates the native Service field into ztunnel's endpoint selection policy.

Unset `spec.infrastructure.labels` and `spec.infrastructure.annotations` inherit the corresponding Gateway metadata independently. Adding only `parametersRef` preserves that inheritance. An explicitly supplied map replaces the corresponding inherited map before resource patches are applied.

The same ConfigMap may also contain `data.config` for Envoy's xDS settings or `data["config.yaml"]` for native agentgateway configuration. These keys are excluded from resource patching. Envoy resource-only ConfigMaps may omit `config` to use default proxy settings; an explicitly empty or invalid `config` retains the last valid proxy configuration. Native agentgateway still requires `config.yaml`; see [Deploy agentgateway](deploy-agentgateway.md).

## Use separate CA and ADS credentials

The Envoy gateway agent uses `AGENTIO_TOKEN_FILE` for ADS authentication. Set `AGENTIO_CA_TOKEN_FILE` to a separate projected ServiceAccount token when the certificate authority requires a different audience. If unset or empty, it uses `AGENTIO_TOKEN_FILE`, preserving the existing shared-token setup. The CA token file is read again on each signing attempt, including certificate renewal.

Use a `deployment` patch to mount the additional projected token and set `AGENTIO_CA_TOKEN_FILE` in `agentio-proxy`. Choose the token audience accepted by the CA. `CA_ADDR`, `AGENTIO_CA_SERVER_NAME`, and `AGENTIO_CA_ROOT_CA` configure the CA connection independently of `AGENTIO_XDS_ADDRESS`, `AGENTIO_XDS_SERVER_NAME`, and `AGENTIO_XDS_ROOT_CA` for ADS.

## Set GatewayClass defaults

Create a ConfigMap in the control-plane namespace (`agentio-system` by default) with the `gateway.agentio.kruise.io/defaults-for-class` label:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: egress-defaults
  namespace: agentio-system
  labels:
    gateway.agentio.kruise.io/defaults-for-class: agentio-egress
data:
  horizontalPodAutoscaler: |
    spec:
      minReplicas: 2
      maxReplicas: 5
  podDisruptionBudget: |
    spec:
      maxUnavailable: 1
```

Class defaults apply first; the Gateway's `parametersRef` patches apply afterward. If multiple class-default ConfigMaps match, the oldest is selected, breaking timestamp ties by name. Class-default ConfigMaps accept only the five resource patch keys; proxy configuration remains per Gateway.

HPA and PDB are generated only when their respective patch key is present in the selected class defaults or per-Gateway ConfigMap. An empty `{}` patch also enables the resource with its template defaults. Removing the key stops applying that resource but does not delete an existing HPA or PDB.

## Gateway addresses

Once the generated Deployment is available and its managed Service exists, the deployer publishes `Gateway.status.addresses` using the address-selection rules from `release-0.1`:

- Service external IPs and LoadBalancer ingress IPs or hostnames take precedence.
- Without external addresses, `agentio-egress` reports both ClusterIPs and the Service hostname, as the waypoint class does in `release-0.1`. `agentio-agentgateway` reports the hostname by default.
- The `networking.istio.io/address-type` Gateway annotation selects `IPAddress` or `Hostname` for internal addresses. It does not filter external addresses.

The internal hostname has the form `<service>.<namespace>.svc.<cluster-domain>` and uses the configured cluster domain, defaulting to `cluster.local`. A headless Service contributes no ClusterIP.

While a LoadBalancer Service has no external address, its internal hostname is omitted and `Programmed` is false with reason `AddressNotAssigned`; eligible internal IPs can still be reported. If no new address can be reported, an already published address is retained. Addresses are also retained while the Deployment is pending or rolling out and when native agentgateway configuration is invalid. Read the `Programmed` condition to distinguish availability from the retained discovery address.

## Updates and errors

ConfigMap creation, updates, and deletion trigger reconciliation. Deployment Pod template changes trigger a rollout; Envoy `config`-only updates use xDS without changing the Pod template. Native `config.yaml` changes still trigger a rollout.

Changing or removing the `gateway.agentio.kruise.io/defaults-for-class` label reconciles Gateways from both the old and new classes. The old class falls back to its next-oldest matching ConfigMap, or to the template if none remain.

Removing a Deployment, Service, or ServiceAccount patch restores the fields owned by the controller to the template plus any remaining class defaults. Gateway deletion allows Kubernetes to garbage-collect owned resources; input ConfigMaps are not adopted or deleted.

Missing parameters, unsupported resource patch keys, invalid patch syntax, or forbidden metadata changes abort rendering and leave previously applied resources in place. The controller logs rendering failures without retrying or writing an `InvalidParameters` condition for these resource patch errors. Kubernetes apply failures return an error to the retry queue. Check `agentiod` logs to diagnose resource patch failures.
